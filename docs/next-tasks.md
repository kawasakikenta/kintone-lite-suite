- 比較 HTML、JSON、PNG などは 7 日間の Actions artifact とし、Git へ追加しない。

## T2. 外部依存の固定（対応済み 2026-11）

ER 図の生成 HTML が実行時 CDN 応答へ依存しないよう、Cytoscape・Dagre・cytoscape-dagre を固定版で同梱した。これで、ER 図以外（下の「T2 のうち ER 図以外の外部依存」）と合わせて T2 全体が対応済みになった。実行時に CDN から読み込むのは、プロセス図の Mermaid（SRI 検証つき）だけである。

- `package.json` で固定している版の配布ファイルを、ビルド時に `ER図.js` へ取り込み（`src/tabs/er-libraries.ts`・`rawTextPlugin.js`）、生成する HTML の head へインラインで埋め込む。`<script src>`・SRI・代替 CDN の後読みは無くなり、CSP の `script-src` も `'unsafe-inline'` だけになった。各ライブラリの著作権・ライセンス表記は残している。
- 「ER図を開く」の画面、「ER図をHTMLで保存」のファイル、図の画面の「出力 → 編集済みHTMLを保存」で保存して開き直したファイルのすべてが、ネットワークを遮断した状態で描画できる（`npm run test:er-compare` が検査）。
- サイズ: `ER図.js` 約 0.47 MB → 約 1.1 MB、生成 HTML は 約 0.67 MB 増える（2 アプリの図で 約 0.25 MB → 約 0.91 MB）。他の 11 本の bundle にライブラリは入らない。
- 描画ライブラリを初期化できなかった場合の表（取得済みアプリの一覧）は残した。文言は CDN を前提にしない。操作バーなどの画面部品が表に重なって見出しが読めなかった問題も直した。
- 残る課題: ライブラリの版を上げるときは `package.json` と `src/tabs/er-libraries.ts` の版の表記を同時に更新する（不一致は単体テストが検出する）。Mermaid（プロセス図）だけが引き続き CDN から読み込む（SRI 検証つき）。

## T2-2. ER 図の探索の高速化と大規模な図（対応済み 2026-11）

- 逆引きの全アプリ走査と幅優先の探索を、同時に 4 アプリ（1 アプリ 3 リクエストのため最大 12 リクエスト）まで並列に読み取るようにした（`ER_DEFAULTS.concurrency`、`tabs/er.ts` の `crawl`）。結果の並び・深さ・関連は 1 アプリずつ読んだときと同じで、深さごとに読み取り、見つけた順に取り込む。1 リクエスト 60 ms の合成 API（300 アプリ）で、逆引きあり 43.1 秒 → 12.2 秒、全アプリ起点 42.4 秒 → 10.5 秒、2 起点からの探索 35.6 秒 → 8.5 秒。
- 「中止」は、読み取りを終えたアプリの数と、中断した・見つけたが読んでいないアプリの数を数えて報告する（中断したアプリは先頭 5 件まで示す）。
- 39 アプリの合成データでの通し検証（`npm run test:er-explore`）で見つけた次の問題を直した。(1) フォース・グリッドなどで、アプリのカードが重なる（縮小時の概要カードは詳細より幅が大きく、配置後に重なっていた。フォースは詳細でも重なっていた）。(2) 検索が、現在の表示密度でカードに出ている項目しか探さない（「結合のみ」では項目名で何も見つからない）。(3) 関連（線）の詳細に、ルックアップのコピーするフィールド・関連レコード一覧の表示フィールド・絞り込み条件・アプリアクションのコピーが無い。(4) 取得失敗の理由に内部の通信情報（`[API] GET …`）が出る。(5) 描画ライブラリを初期化できないときの案内の表が、操作バーなどに隠れる。
- 残る課題: 実際の kintone での同時 4 アプリ（最大 12 リクエスト）の確認。応答が遅い・429 が返る環境では `apiGet` の再試行で吸収するが、頻発するなら `ER_DEFAULTS.concurrency` を下げる。数千アプリの図は、描画に時間がかかり HTML も大きくなる（確認画面に注意を出している）。

### T2 のうち ER 図以外の外部依存（対応済み。ER 図は上のとおり）

kintone の画面へ読み込む外部スクリプトをなくす・検証できるものだけにする作業を、ER 図以外のツールで行った。

- ZIP 作成（以前は JSZip を cdnjs から読み込み）: 自前の実装 `src/archive/lite-zip.ts` に置き換え、通信しなくした。ページの `window.JSZip` も使わない。classic ZIP の上限（4GB 未満・65,535 件）は ZIP 作成時に明確なエラーにする。
- 設計書 Excel（以前は xlsx-js-style を jsDelivr から読み込み）: `設計書作成.js` にだけ同梱した。SheetJS のフォールバックは廃止。
- プロセス図の Mermaid（約 3MB のため同梱せず）: 固定版を SRI（sha384）と `crossorigin="anonymous"` つきで jsDelivr → unpkg の順に読み込む。cdnjs は npm の配布物と同じ内容と確かめられないため外した。
- 残った課題:
  - 添付ファイルのバックアップなどで ZIP が 4GB に達しそうなときに、取得済みの分で自動的に区切る（今は ZIP の作成時にエラーで止まり、取得済みの分が保存されない）。
  - 圧縮・CRC の計算は 1 エントリずつ非同期で行うが、「中止」は ZIP の作成中には効かない（作成前の取得は中止できる）。
  - Mermaid も同梱できるか（サイズ約 3MB を許容するか）。同梱すれば CDN が遮断された環境でもプロセス図を描ける。
  - 実環境（CDN に届くネットワーク）で、Mermaid の配布物が固定したハッシュと一致することの確認（この開発環境からは CDN へ届かず、npm の配布物から計算した値のみ確認した）。

### T4 の実環境での確認結果（2026-10-31）

Yu5 テナントのテスト専用アプリ（62・63）で確認した。書き込みはアプリ 63 のプレビューのみで、確認後に変更を中止した。

- 「変更を中止」した後のプレビューの revision は本番と同じ値に戻る（未公開の変更の判定に使える）。
- リマインダー通知が無いアプリの `timezone` は `null`。`timezone: null` の PUT は受け付けられ、kintone が既定値を入れる（空文字は拒否）。
- カテゴリーは名前をキーにしたオブジェクトで、階層は `children`（配列は `CB_IJ01`、キーと `name` の不一致は `GAIA_NM01`、`index` と `children` は必須）。カテゴリーが無いアプリは `categories: {}`。
- 反映元と反映先で先頭のステータスが違うと、プロセス管理の PUT は「先頭のステータスは、先頭以外の位置に変更できません」で拒否されることがある（差分確認で警告する）。
- 通知先の `FIELD_ENTITY` を含むリマインダー通知の PUT と、一度失敗した後の別の PUT の revision 引き継ぎは正常に動く。

- 一般設定の PUT は受け付けられる。レコードのタイトルは `AUTO` なら `code` を送らないか既存フィールド以外でも無視される（空文字の `code` は `CB_VA01` で拒否。反映ツールは AUTO では `code` を送らない）。`MANUAL` は `code` 必須で、存在しないフィールドは `GAIA_FC01`。数値の桁数は `digits` 31 が `CB_VA01`、小数部が全体を超えると `GAIA_IL04`。年度の開始月 13 は `CB_VA01`。
- Webhook を読み取る公開 REST API は無い（`/k/v1/app/webhook.json` は HTML の 404）。設計書では取得せず、サマリーに対象外と明記する。

## T6. 環境内の全アプリを対象にする機能の実環境確認と残課題（2026-10 追加）

全 11 ツールに「環境内の全アプリ」（アプリ検索）と、複数アプリへの一括処理を追加した。合成 API・単体テスト・画面ハーネスでのみ検証している。数百〜数千アプリの環境で次を確認する。

- 差分比較の 1対多（対応済み、2026-11 測定）: 比較先ごとに比較先バンドルと差分行を保持する（比較元は 1 つを共有）。業務アプリ規模（フィールド約 200・設定 JSON 約 84KB・JS/CSS の本文 5 ファイルで約 485KB）の比較先 200 件で、保持量は約 99MB（1 件あたり約 505KB）だった（Chromium の `performance.memory`、`gc()` 後の差）。大半は JS/CSS の本文（`_bodyText`）とプラグイン設定の取得結果で、比較後は出力が読まない作業用の値のため、保持前に取り除いた（`diff/retention.ts`）。変更後は約 22MB（約 114KB。残りは設定そのもの）で、行からの HTML・Excel・Markdown の保存内容は 1対1 の結果と同じ（`npm run test:diff-explore` で毎回確認）。外挿では、同じ規模の比較先 1,000 件で約 500MB → 約 110MB、5,000 件で約 2.5GB → 約 0.55GB。設定そのものの保持（約 1.3 倍）は残るため、比較先が数千件になる場合は、差分 0 件の比較先を保持せず必要時に再取得する（再取得になることを利用者へ示す）、一定件数ごとに分けて実行する、などを検討する。100 件を超えると時間とメモリの注意を出す今の案内は維持する。

## T7. 本番反映の実環境確認（2026-11 追加）

本番反映ツール（`tools/本番反映.js`）は、合成エンジン・合成 API・単体テスト・画面ハーネスでのみ検証している。本番へ書き込むため、テスト専用アプリで次を確認する（確認後は、バックアップJSONをプレビュー反映で読み込んで戻す）。

- GAIA_CO02：差分確認の後にプレビューが更新されたアプリへ、確認時の revision を添えて反映を依頼したとき、`GAIA_CO02`（競合）になるか。同じ revision の再送（自動再試行はしない）で何が起きるか。
- FAIL 時の理由の取得：反映状況の取得（`GET /k/v1/preview/app/deploy.json`）が `FAIL` を返したとき、失敗の理由を取得できるか。取得できない場合の「失敗」の案内の十分さ。

- ゲストスペース：ゲストスペースのアプリの反映・中止・バックアップ（JS/CSS ファイルの取得を含む）が通常スペースと同じように動くか。

## T8. 反映元アプリから本番へ の実環境確認（2026-11 追加）

本番反映ツールの「反映元アプリから本番へ」（差分の選択・修正と、プレビューへの書き込みに続く本番への反映）は、合成エンジン・単体テスト・画面ハーネスでのみ検証している。本番へ書き込むため、テスト専用アプリ（反映元 1 つ・反映先 1 つ）で、書き込み後にバックアップから戻して確認する。

- 設定値 1 つずつの反映：フィールドの「必須」だけを選んで表示名を選ばなかったとき、反映先の表示名が変わらず、必須だけが変わるか。選択肢・ルックアップ・テーブル内フィールド・一覧の並び順など、項目ごとの粒度が意図どおりか。
- 要素ごとの追加（whole）：選ばなかったフィールドを参照する一覧・グラフ・アクションを選んだとき、組み合わせの問題として止まるか。選ぶと一緒に選ばれる変更（requires）が、実際に反映できる順序になっているか。
- 入力欄とJSONでの修正：入力欄で直した値（表示名・必須・選択肢など）が、そのまま反映先のプレビューに書き込まれるか。JSON で直した内容が、選択・入力欄より優先されるか。フィールドの種類・コードの変更やフィールドの削除をエンジンが止めるか。
- 連続反映：プレビューへの書き込みの直後に、そのまま本番へ反映（アプリを更新）できるか。本番へ反映する前の本番の revision と、プレビューへ書き込んだあとの revision が一致するか。書き込みの revision を引き継いで GAIA_CO02（競合）にならないか。
- 反映先プレビューの未公開の変更：以前からの未公開の変更があるとき・確認できなかったとき、了承がなければ本番へ反映しないか。了承したときは、その未公開の変更も一緒に本番へ反映されるか。
- バックアップ：反映前のプレビューと、本番へ反映する前の本番の 2 つの JSON が保存されるか。どちらもプレビュー反映の反映元（設定JSON）に読み込んで戻せるか。
- 「プレビューまで」と、本番へ反映しなかった場合：目標をプレビューまでにしたとき本番が変わらないか。本番へ反映しなかったあと、「プレビューの変更を公開」から続きを実行できるか。
- 件数が多いとき：数千件の変更（アクション・一覧・アクセス権など）で、差分の選択・絞り込み・全選択・入力欄の描画が固まらないか。
- 選んだ変更と修正の保存・読み込み（合成環境では対応済み）：保存したファイルを、別の担当者が別のブラウザで、同じ反映元・反映先から差分を抽出し直して読み込んだとき、選択・入力欄の修正が戻るか。抽出し直した差分が保存時と食い違うとき（反映先が更新された）に、当てはまらなかった件数が実際の差と合うか。JSON での修正は、反映先が保存時から変わっていないときだけ戻るか（反映先の設定の指紋が、kintone が返す設定の並び順・数値の表記の揺れで変わらないか）。数百〜数千件の選択を保存したファイルのサイズと読み込みの時間。
- 反映後の内容の確認（合成環境では対応済み）：本番へ反映した直後に「反映後の内容を確認する」を押して、選んだ変更がすべて「反映されています」になるか。kintone が足す既定値・数値と文字列の表記の揺れ・フィールドの種類ごとの正規化（選択肢の index・lookup の `relatedApp.code`・テーブル内フィールド・計算式の表記など）で、反映できている値が「反映されていない変更」と出ない（偽陽性）ことを、項目ごとに確かめる。偽陽性が出る項目があれば、期待した値との比べ方（`deploy/sourceVerify.ts` の `satisfiesExpected`）を項目ごとに調整する。JS/CSS はファイル名だけで比べているため、ファイルの中身が反映されたかの確認方法を検討する。完了を確認できなかった結果（kintone が処理中）で、確認した時点では「反映されていない」と出て、処理が終わったあとの確認し直しで「反映されています」に変わるか。
