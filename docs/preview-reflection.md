# プレビュー反映

`tools/プレビュー反映.js` は、アプリまたは設定JSONを反映元にして、指定アプリのプレビュー設定を更新します。本番公開はアプリ設定画面で行います。

## 操作の流れ

1. **対象を選ぶ**：反映元・反映先のIDを指定します。アプリのURL（`/k/123/`、`/k/guest/5/123/`、`?app=123`）を貼り付けるとアプリIDとゲストスペースIDを読み取ります。反映元の取得環境は「本番設定」「プレビュー設定」から選びます。初期選択はフィールド・レイアウト・一覧の3項目です。「差分を確認する」へ進めない場合は、画面下部に「次に進むには：…」として不足している入力を表示します。
2. **差分を確認**：APIで確認したアプリ名・ID・ゲストスペース・取得環境を表示します。項目ごとの「内訳」を開くと、反映先の現在と反映後を比較できます。追加・変更・削除・保持を区別し、不要な項目をチェックから外せます。
3. **最終確認**：書き込み先と反映項目を確認してチェックを入れます。削除・置換、権限・通知・プロセス変更、同じアプリの本番からプレビューへの反映では、反映先IDも入力します。ID入力中のEnterでは実行されません。
4. **反映結果**：成功・失敗・未実行を確認します。「反映後の差分を再確認」で反映した項目を同じ条件で再取得し、反映先が反映元と一致したか（差分が残っていないか）を確認できます。書き込みは行いません。失敗した場合は「失敗・未実行だけ選択」から対象を選び、差分を再取得してから再実行できます。

一覧検索にはフィールドコードや変更前後の値も使えます。「反映計画JSONを保存」には選択範囲の変更内訳と送信予定の設定を全件収録します。画面の長文は省略表示し、内訳は50件ずつ追加表示します。

### 詳細設定とプリセット

- **参照先変換（ルックアップ）**：1行に「旧AppID → 新AppID」（区切りは `→` / `->` / `=` / `:` / カンマ / 空白）で入力します。従来の `{"旧AppID":"新AppID"}` 形式のJSONも使えます。入力欄の下に件数、または読み取れない行を表示します。
- **プリセット**：接続先・反映項目・参照先変換・保持設定に名前を付けて保存します。ブラウザには永続保存しないため、次回も使う場合は「JSONで書き出し」で保存し、「JSONを読み込み」で復元します。同名のプリセットは読み込んだ内容で置き換えます（最大30件）。

## 何を保持し、何を置き換えるか

| 項目 | 反映する内容 |
| --- | --- |
| フィールド | 不足分を追加し、変更のある定義だけ更新。反映先だけのフィールド・テーブル内フィールドは保持。種類の変更、コードの改名、テーブル間の移動は事前に停止 |
| レイアウト | 反映元の配置を適用。反映先だけのフィールド配置はフォーム・グループ・テーブルの末尾に保持。装飾要素を含む配置の置換は内訳に表示 |
| 一覧・グラフ・アクション | 標準では反映先だけの名前を持つ設定を保持し、表示順を反映元の後へ配置。「保持する」をOFFにした場合は反映元にない設定を削除。フィールドの保持はOFFにならない |
| プラグイン | まだ追加されていないIDだけ追加。反映先のプラグインは削除しない。プラグイン固有の設定値はコピーしない |
| JS/CSS | 適用範囲とPC・モバイルの一覧を更新。FILEは反映先プレビューですでに使われているキーのみ使用。別アプリのFILEは反映先へアップロードしてから再比較 |
| 権限・通知・プロセス・カテゴリー | 選択した設定を置換。通知先やルール、状態、カテゴリーなどの削除・変更を確認画面に表示。カテゴリーの有効状態、コメント通知、リマインダーのタイムゾーンも対象 |

「変更件数」は設定値・配列要素の差分件数です。レコードの削除件数ではありません。配列要素の入れ替えは削除と追加で示すことがあります。

## 実行前の検査とバックアップ

取得に失敗した項目は自動除外せず、選択されたままなら最終確認へ進めません。取得し直すか、利用者が対象から外します。一覧・レイアウトが参照するフィールドの不足、設定形式の不足、revision欠落も検出します。ルックアップ変換先が確認できない場合は書き込みを始めません。

実行直前に反映元と反映先を再取得し、確認時の内容・revisionと照合します。条件変更、外部更新、取得途中のrevision不一致があれば中断します。反映中は更新応答のrevisionを次の書き込みへ引き継ぎ、エラー時には残りの処理を止めます。

最初の書き込み前に、再取得して照合した反映先設定のJSONバックアップのダウンロードを開始します。ブラウザが端末への保存を完了したことまでは検証できません。JSONにはJS/CSSファイル本体とプラグイン固有設定を含みません。元のファイルは別途保管してください。複数APIへの更新は一括取消できず、フィールド追加などはバックアップJSONの再反映だけでは完全に元へ戻りません。

確認画面から戻った場合や条件・対象を変更した場合は、最終確認のチェックとID入力を解除します。反映後も比較結果を使い回さず、再取得を要求します。

## 公式APIに基づく実装

- 一覧の省略項目は削除されるため、保持モードでは反映先の項目を送信設定に含めます。[一覧の設定を変更する](https://cybozu.dev/ja/kintone/docs/rest-api/apps/view/update-views/)
- アクションでも、送信しない名前の設定は削除されます。[アクション設定を変更する](https://cybozu.dev/ja/kintone/docs/rest-api/apps/settings/update-action-settings/)
- フィールドは追加と更新のAPIを分け、レイアウトには既存フィールドの配置を残します。[フィールド追加](https://cybozu.dev/ja/kintone/docs/rest-api/apps/form/add-form-fields/)、[フィールド更新](https://cybozu.dev/ja/kintone/docs/rest-api/apps/form/update-form-fields/)、[レイアウト更新](https://cybozu.dev/ja/kintone/docs/rest-api/apps/form/update-form-layout/)
- プラグイン追加はPOSTと`ids`を使用します。[アプリにプラグインを追加する](https://cybozu.dev/ja/kintone/docs/rest-api/apps/settings/add-app-plugins/)
- JS/CSSの適用範囲と、同じプレビュー設定で使用中のFILEキーの扱いに従います。[カスタマイズ設定を変更する](https://cybozu.dev/ja/kintone/docs/rest-api/apps/settings/update-customization/)
- 通知の`notifyToCommenter`とカテゴリーの`enabled`を引き継ぎます。[一般通知](https://cybozu.dev/ja/kintone/docs/rest-api/apps/settings/update-general-notification-settings/)、[カテゴリー](https://cybozu.dev/ja/kintone/docs/api-lab/rest-api/apps/update-categories/)

## 開発時の検証

`npm run check`で型検査・単体テスト・ビルド、`npm run test:reflect-dom`で画面と実エンジンを接続した合成APIテストを実行します。確認のやり直し、誤入力、進めない理由の表示、URL貼り付け、参照先変換の行形式、プリセットの書き出し・読み込み、削除確認、二重クリック、Enter、参照不足、取得失敗、外部更新、送信先・revision、バックアップ順序、反映後の再確認、320〜1440pxの表示を検証します。実kintone環境への書き込みテストは行いません。
