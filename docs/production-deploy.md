# 本番反映

`tools/本番反映.js` は、アプリのプレビューにある未公開の変更を、本番へ公開（kintone の「アプリを更新」）するか、破棄（「変更を中止」）するためのツールです。本番とプレビューの差分をアプリごとに確認し、反映前の本番設定をバックアップしてから実行します。複数アプリ（環境内の全アプリを含む）をまとめて扱えます。

プレビューへの書き込みはプレビュー反映・フィールド追加・JS/CSS設定が行い、このツールはその次の「本番へ公開する」段階だけを担当します。見出しのバッジは「本番の設定を変更」です。

## 操作の流れ

4 段階で進みます。段階 1 と 2 では何も書き込みません。

1. **対象を選ぶ**
   - 「対象アプリ」の表に、アプリID（ゲストスペースはアプリごとに指定）を入れます。URL やカンマ区切りの貼り付け、「現在のアプリ」ボタン、「アプリを検索」の「環境内の全アプリ」（「候補 N 件をすべて対象アプリに追加」）から追加できます。最大 1000 件です。
   - 「操作」で「本番へ反映（アプリを更新）」（既定）か「変更を中止（プレビューを本番に戻す）」を選びます。
   - 「詳細設定…」で反映の方法（1アプリずつ／まとめて）と、失敗したときの動作を選びます。現在の値は表面に 1 行で示します。
   - 進めない理由は「次に進むには：…」と固定フッターに出ます。「未公開の変更を確認する」で段階 2 へ進みます。
2. **変更を確認**
   - 本番とプレビューの差分を、アプリごとに表で確認します。この画面では書き込みません。
   - 「計画をMarkdownで保存」「計画のMarkdownをコピー」で、承認依頼などに貼れる計画を出力できます。
3. **最終確認**
   - 方向・対象・反映の方法・削除される設定・削除されるフィールド・バックアップ・取り消し方を示します。
   - 「上記の内容を確認しました」のチェックと、確認入力（1 件なら対象アプリのID、複数なら対象のアプリ数）が揃うと、実行ボタンが押せます。入力欄で Enter を押しても実行しません。
4. **結果**
   - 実行中はアプリごとの状態を更新します。完了後は、結果JSON・記録のMarkdown・バックアップのファイル名を確認できます。

## 確認の流れ（段階 2）

アプリの状態は次の 4 つです。

| 状態 | 意味 | 扱い |
| --- | --- | --- |
| 変更あり | 本番とプレビューの revision が異なる | 既定で選択。実行の対象にできる |
| 未公開の変更なし | revision が一致 | 反映の必要がないため選択できない |
| 取得失敗 | 本番またはプレビューの設定を取得できない | 既定で選択したまま。選択している間は次へ進めない |
| 反映処理中 | kintone が反映を処理中 | 既定で選択したまま。選択している間は次へ進めない |

- 取得失敗・反映処理中のアプリは自動では除外しません。「取得失敗・処理中だけ確認し直す」で再取得するか、「対象から外す」（または選択の解除）を行うまで、最終確認へ進めません。
- 表には、状態・変更のある項目名・削除される設定の件数・revision（本番 → プレビュー）を示します。「詳細を表示」を押すと、項目ごとの「変更の要約」（削除・変更・追加）が開きます。詳細は開いたときに描画するため、数千アプリでも重くなりません。表は先頭 200 件を描画し、「さらに表示」で続きを出します。問題のあるアプリ（取得失敗・反映処理中）は先頭に並びます。
- 「変更を中止」を選んだ場合、見出しは「破棄される変更」に読み替えます。
- 「設定の内容は同じです（revision だけが異なります）」と出たアプリは、反映しても設定は変わりません。

### 削除されるフィールド

本番にあってプレビューに無いフィールドは「削除されるフィールド」として警告色で示します。**本番へ反映すると、そのフィールドのレコードの値も削除され、元に戻せません。** 表の「削除」列は「削除される設定の件数 / フィールド N 件（値も削除）」の形で示します。グループと関連レコード一覧は値を持たないため、削除されるフィールドには数えません（フィールド設定の変更の要約には「削除」として出ます）。削除されるテーブルは 1 件として数え、中のフィールドは別に数えません。

kintone の REST API では、フィールドコードを変えただけの変更も「削除＋追加」に見えます。種類と表示名が同じで本番に無いコードのフィールドがプレビューにある場合は、「フィールドコードを変えただけなら値は残る可能性があります（プレビューの『X』）」と添えます。ただし、コードの変更で値が残るかどうかは、本番へ反映する前には断定できません。

「変更を中止」では、フィールドの削除警告は出しません（プレビューで削除されたフィールドは本番の状態に戻ります）。

## 反映の方法

| 設定 | 動作 |
| --- | --- |
| 1アプリずつ反映（既定） | 1 アプリずつ反映を依頼し、完了を確認してから次へ進みます。 |
| まとめて反映 | 1 回の依頼にまとめます。すべて成功したときだけ本番へ反映され、1 件でも失敗するとすべて取り消されます。最大 300 件・同じゲストスペースのアプリだけ選べます。 |

1アプリずつ反映するときは、失敗したときの動作を選べます。

- **残りを実行しない（既定）**：失敗・確認後の更新・完了を確認できないアプリが出たら、残りは「未実行」にします。
- **残りも続ける**：失敗したアプリがあっても残りを続けます。

実行を始めるときに、対象のすべてのアプリで本番とプレビューの revision を再確認します。差分確認の後に更新があったアプリが 1 件でもあれば、どのアプリにも依頼せず「反映前の確認で止めました」とし、そのアプリを「確認後に更新」で示します（バックアップも保存しません）。1アプリずつ反映するときは、各アプリの依頼の直前にも同じ確認を行い、更新があったアプリは依頼せず「確認後に更新」にします。依頼には確認時のプレビューの revision を添えるため、その後に更新された場合も kintone が受け付けません。

### 結果の状態

| 表示 | 意味 |
| --- | --- |
| 待機中 / 確認中… / 反映中… | 実行中の状態 |
| 成功 | 反映（または中止）が完了した |
| 失敗 | kintone が失敗を返した、または依頼が拒否された |
| 取り消し（ほかのアプリの失敗） | まとめて反映で、ほかのアプリの失敗のため kintone が取り消した |
| 確認後に更新 | 差分確認の後に本番またはプレビューが更新された。依頼していない |
| 完了を確認できない | 依頼したが、時間切れ・中止・状態の取得失敗で完了を確認できない。kintone 側で処理が続く場合がある |
| 未実行 | 中止・前の失敗・事前検査で止めたため実行していない |

実行後のメッセージは、成功数・失敗数・理由の順に示します。

- 例（部分成功）：「4 アプリ中 1 アプリを反映しました。失敗 1 アプリ、未実行 2 アプリ（App 102: 権限がありません）。『失敗・未実行だけ選び直す』から確認し直してください。」
- 例（中止）：「中止しました（3/10 アプリを反映、残り 7 アプリは未実行）。」依頼済みのアプリは kintone 側で処理が続く場合があります。
- 反映前の確認（事前検査・バックアップ）で止めたときは、「反映前の確認で止めました。まだ本番へは反映していません。」から始めて理由を示します。
- 反映後に本番とプレビューの revision が一致しないアプリは、成功でも注意として示します。

「失敗・未実行だけ選び直す」は、成功以外のアプリを対象に段階 1 へ戻します。差分は取り直して確認します。

件数が多いとき（200 件超）は、実行結果の一覧を全件描画せず、件数の要約と、問題のあるアプリ・処理中のアプリを優先して表示します。全件は「結果JSONを保存」で確認できます。

## バックアップと戻し方

- 本番へ反映する前に、反映前の本番設定を JSON で保存します（変更のある JS/CSS はファイル本体も含みます）。「変更を中止」では、中止前のプレビューの設定を保存します。
- バックアップの形式はプレビュー反映の設定 JSON と同じです。プレビュー反映の反映元（設定JSON）にそのまま読み込めます。
- バックアップを保存できない場合は反映しません（「反映前の確認で止めました」）。本体を保存できなかった JS/CSS ファイルは、結果画面に一覧で示します。
- **本番へ反映した後の戻し方**：バックアップJSONをプレビュー反映の反映元（設定JSON）に読み込んでプレビューへ戻し、このツールで本番へ反映します。**本番への反映は取り消せません。削除したフィールドの値は戻りません。**
- **変更を中止した後の戻し方**：破棄した変更は、バックアップJSONをプレビュー反映で読み込むと戻せます。

## 制約

- 対象アプリは最大 1000 件です。まとめて反映は最大 300 件・同じゲストスペースのアプリだけです。
- 本番への反映と「変更を中止」を行うには、対象アプリのアプリ管理権限が必要です。
- 反映の依頼は 1 件ずつ（または 1 回のまとめ）送り、自動では再試行しません。通信が途切れた場合は「完了を確認できない」として示し、アプリの設定画面で状態を確認します。
- 本番反映では書き込みガードの例外として、`/app/deploy.json` への POST（プレビュー側の prefix・完全一致）だけを許可します。レコード API やほかの本番設定への書き込みは行いません。
- ブラウザの永続ストレージは使いません。画面の状態はメモリだけに持ち、再読み込みで消えます。

## 開発時の検証

```bash
cd tools/統合ツール && npm run check   # 型検査・単体テスト（deploy/display・report を含む）・ビルド
npm run test:deploy-dom -- --browser chromium
```

`test:deploy-dom` は、エンジンを合成エンジンに差し替えて、画面の 4 段階・進めない理由・差分確認の表示・取得失敗を選んだままでは進めないこと・最終確認の入力と Enter・条件変更での確認解除・実行中の状態更新・成功／部分失敗／blocked／中止の表示・二重実行防止・Markdown と JSON の保存・1000 件の実行・320〜1440px の横はみ出しを実ブラウザで検証します。実アプリには通信せず、画面と結果は `.iter-shots/deploy-lite-dom/`（Git 管理外）に保存します。

同じコマンドの後半（`tools/test-harness/deploy-engine-scenarios.cjs`）では、エンジンを差し替えず、画面と実エンジンを束ねたまま、通信（`kintone.api`・`fetch`）だけを合成 kintone に差し替えて検証します。合成 kintone は、本番とプレビューの全比較項目の GET（revision はアプリ単位）、`POST /preview/app/deploy.json`（確認時のプレビュー revision と食い違えば `GAIA_CO02` で拒否。受け付けたら PROCESSING → SUCCESS／FAIL／CANCEL。revert ならプレビューを本番へ戻す）、状態確認の GET、ファイル本体の GET を再現し、それ以外の書き込みと想定外の URL は例外にして失敗させます。確認する内容は次のとおりです。各シナリオで、書き込みが deploy.json の POST だけであることも確認します。

- 1 アプリの本番反映：削除フィールドの警告、依頼は 1 回で確認時の revision を添えること、バックアップ（反映前の本番）の保存が依頼より前であること、成功後に本番とプレビューの revision が一致すること。
- 未公開の変更なし（revision 一致）のアプリは選べず、設定本体を取得しないこと。
- 確認後（最終確認から実行まで、または 1 アプリずつの実行の途中）にプレビューが更新されたとき、該当アプリは依頼せず「確認後に更新」にし、実行前なら何も依頼せずバックアップも保存しないこと。
- 1 アプリずつ反映で 2 件目が失敗したとき、3 件目を依頼しないこと。依頼が権限エラーで拒否されたとき「失敗」にすること。
- まとめて反映で 1 件失敗したとき、依頼は 1 回で全件を含み、ほかは「取り消し」になること。
- 変更を中止：`revert: true`、バックアップは中止前のプレビュー（`environment: 'preview'`）。
- JS/CSS：反映で外れるファイルの本体を取得できないときは依頼せず止め、取得できるときはバックアップの `file._content` に埋め込むこと。
- ゲストスペースのアプリは `/k/guest/{id}/v1/...`（設定・依頼・状態確認・ファイル本体）を使うこと。
- 実行中の「中止」：依頼の前なら依頼せず未実行、完了待ちの途中なら「完了を確認できない」にすること。

画面は `src/entries/deploy-lite-ui.ts`、表示用の純粋関数は `src/deploy/display.ts`、計画・記録・結果 JSON の組み立ては `src/deploy/report.ts`、エンジンとの取り決めは `src/deploy/types.ts` です。
