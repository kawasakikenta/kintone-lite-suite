# 本番反映

`tools/本番反映.js` は、アプリのプレビューにある未公開の変更を、本番へ公開（kintone の「アプリを更新」）するか、破棄（「変更を中止」）するためのツールです。本番とプレビューの差分をアプリごとに確認し、反映前の本番設定をバックアップしてから実行します。複数アプリ（環境内の全アプリを含む）をまとめて扱えます。

プレビューへの書き込みはプレビュー反映・フィールド追加・JS/CSS設定が行い、このツールの「プレビューの変更を公開」は、その次の「本番へ公開する」段階だけを担当します。別のアプリ（開発・検証用）の設定を、差分を選んで本番へ反映するときは、「反映元アプリから本番へ」を使います（[後述](#反映元アプリから本番へ開発検証用アプリの設定を選んで反映する)）。見出しのバッジは「本番の設定を変更」です。

## 操作の流れ（プレビューの変更を公開）

パネル上部の「操作」で「プレビューの変更を公開」を選ぶと、次の流れです。4 段階で進みます。段階 1 と 2 では何も書き込みません。

1. **対象を選ぶ**
   - 「対象アプリ」の表に、アプリID（ゲストスペースはアプリごとに指定）を入れます。URL やカンマ区切りの貼り付け、「現在のアプリ」ボタン、「アプリを検索」の「環境内の全アプリ」（「候補 N 件をすべて対象アプリに追加」）から追加できます。最大 1000 件です。
   - 「操作」で「本番へ反映（アプリを更新）」（既定）か「変更を中止（プレビューを本番に戻す）」を選びます。
   - 「詳細設定…」で反映の方法（1アプリずつ／まとめて）と、失敗したときの動作を選びます。現在の値は表面に 1 行で示します。
   - 進めない理由は「次に進むには：…」と固定フッターに出ます。「未公開の変更を確認する」で段階 2 へ進みます。
2. **変更を確認**
   - 本番とプレビューの差分を、アプリごとに表で確認します。この画面では書き込みません。
   - 「計画をMarkdownで保存」「計画のMarkdownをコピー」で、承認依頼などに貼れる計画を出力できます。
3. **最終確認**
   - 方向・対象・反映の方法・削除される設定・削除されるフィールド・バックアップ・取り消し方を示します。
   - 「上記の内容を確認しました」のチェックと、確認入力（1 件なら対象アプリのID、複数なら対象のアプリ数）が揃うと、実行ボタンが押せます。入力欄で Enter を押しても実行しません。
4. **結果**
   - 実行中はアプリごとの状態を更新します。完了後は、結果JSON・記録のMarkdown・バックアップのファイル名を確認できます。
   - 反映（または中止）が成功した（完了を確認できなかった場合を含む）アプリがあるときは、「バックアップから戻す」を出します。押すと「反映元アプリから本番へ」に切り替え、そのバックアップの内容を戻す設定にして段階 1 を表示します（[後述](#バックアップと戻し方)）。複数アプリを反映したときは、戻すアプリを選びます。

## 確認の流れ（段階 2）

アプリの状態は次の 4 つです。

| 状態 | 意味 | 扱い |
| --- | --- | --- |
| 変更あり | 本番とプレビューの revision が異なる | 既定で選択。実行の対象にできる |
| 未公開の変更なし | revision が一致 | 反映の必要がないため選択できない |
| 取得失敗 | 本番またはプレビューの設定を取得できない | 既定で選択したまま。選択している間は次へ進めない |
| 反映処理中 | kintone が反映を処理中 | 既定で選択したまま。選択している間は次へ進めない |

- 取得失敗・反映処理中のアプリは自動では除外しません。「取得失敗・処理中だけ確認し直す」で再取得するか、「対象から外す」（または選択の解除）を行うまで、最終確認へ進めません。
- 表には、状態・変更のある項目名・削除される設定の件数・更新番号（本番 → プレビュー）を示します。更新番号は、kintone がアプリの設定を保存するたびに増える番号（revision）です。「詳細を表示」を押すと、項目ごとの「変更の要約」（削除・変更・追加）が開きます。詳細は開いたときに描画するため、数千アプリでも重くなりません。表は先頭 200 件を描画し、「さらに表示」で続きを出します。問題のあるアプリ（取得失敗・反映処理中）は先頭に並びます。
- 「変更を中止」を選んだ場合、見出しは「破棄される変更」に読み替えます。
- 「設定の内容は同じです（更新番号だけが異なります）」と出たアプリは、反映しても設定は変わりません。

### 削除されるフィールド

本番にあってプレビューに無いフィールドは「削除されるフィールド」として警告色で示します。**本番へ反映すると、そのフィールドのレコードの値も削除され、元に戻せません。** 表の「削除」列は「削除される設定の件数 / フィールド N 件（値も削除）」の形で示します。グループと関連レコード一覧は値を持たないため、削除されるフィールドには数えません（フィールド設定の変更の要約には「削除」として出ます）。削除されるテーブルは 1 件として数え、中のフィールドは別に数えません。

kintone の REST API では、フィールドコードを変えただけの変更も「削除＋追加」に見えます。種類と表示名が同じで本番に無いコードのフィールドがプレビューにある場合は、「フィールドコードを変えただけなら値は残る可能性があります（プレビューの『X』）」と添えます。ただし、コードの変更で値が残るかどうかは、本番へ反映する前には断定できません。

削除されるフィールドがあるアプリは、本番のレコード数も読み取って、影響の大きさを示します（差分確認の詳細と最終確認）。「このアプリのレコード: N 件（閲覧できるレコードの数）。削除するフィールドの値は、これらのレコードから削除されます。」の形で、レコード API の GET（`totalCount=true`・`limit 1`）だけを使い、書き込みません。件数は閲覧できるレコードの数です（kintone は閲覧権限のないレコードを数えません）。レコードを閲覧できない・取得に失敗したときは「レコード数は確認できませんでした（理由）。削除するフィールドの値は、すべてのレコードから削除されます。」と示し、確認は止めません。最終確認で読み取るのは、削除されるフィールドがあるアプリの先頭 20 件までです（残りは件数だけ示します）。フィールドごとの「値が入っているレコード数」は、クエリの書き方がフィールドの種類で変わるため扱いません。「反映元アプリから本番へ」は、フィールドを削除しないため、この表示はありません。

「変更を中止」では、フィールドの削除警告は出しません（プレビューで削除されたフィールドは本番の状態に戻ります）。

## 反映の方法

| 設定 | 動作 |
| --- | --- |
| 1アプリずつ反映（既定） | 1 アプリずつ反映を依頼し、完了を確認してから次へ進みます。 |
| まとめて反映 | 1 回の依頼にまとめます。すべて成功したときだけ本番へ反映され、1 件でも失敗するとすべて取り消されます。最大 300 件・同じゲストスペースのアプリだけ選べます。 |

1アプリずつ反映するときは、失敗したときの動作を選べます。件数が多い（20 件以上）ときは、最終確認の「反映の方法」に所要時間の目安（「1 アプリずつ反映すると、1 件あたり数秒、全体で約 N 分かかる見込みです」。1 件 3 秒で計算）を示します。完了待ちの最初の確認は 0.3 秒後、以降は 1 秒から 1.5 倍ずつ（上限 5 秒）に間隔を空けるため、小さなアプリは数百ミリ秒で次へ進みます。

- **残りを実行しない（既定）**：失敗・確認後の更新・完了を確認できないアプリが出たら、残りは「未実行」にします。
- **残りも続ける**：失敗したアプリがあっても残りを続けます。

実行を始めるときに、対象のすべてのアプリで本番とプレビューの revision を再確認します。差分確認の後に更新があったアプリが 1 件でもあれば、どのアプリにも依頼せず「反映前の確認で止めました」とし、そのアプリを「確認後に更新」で示します（バックアップも保存しません）。1アプリずつ反映するときは、各アプリの依頼の直前にも同じ確認を行い、更新があったアプリは依頼せず「確認後に更新」にします。依頼には確認時のプレビューの revision を添えるため、その後に更新された場合も kintone が受け付けません。

### 結果の状態

| 表示 | 意味 |
| --- | --- |
| 待機中 / 確認中… / 反映中… | 実行中の状態 |
| 成功 | 反映（または中止）が完了した |
| 失敗 | kintone が失敗を返した、または依頼が拒否された |
| 取り消し（ほかのアプリの失敗） | まとめて反映で、ほかのアプリの失敗のため kintone が取り消した |
| 確認後に更新 | 差分確認の後に本番またはプレビューが更新された。依頼していない |
| 完了を確認できない | 依頼したが、時間切れ・中止・状態の取得失敗で完了を確認できない。kintone 側で処理が続く場合がある |
| 未実行 | 中止・前の失敗・事前検査で止めたため実行していない |

実行後のメッセージは、成功数・失敗数・理由の順に示します。

- 例（部分成功）：「4 アプリ中 1 アプリを反映しました。失敗 1 アプリ、未実行 2 アプリ（App 102: 権限がありません）。『失敗・未実行だけ選び直す』から確認し直してください。」
- 例（中止）：「中止しました（3/10 アプリを反映、残り 7 アプリは未実行）。」依頼済みのアプリは kintone 側で処理が続く場合があります。
- 反映前の確認（事前検査・バックアップ）で止めたときは、「反映前の確認で止めました。まだ本番へは反映していません。」から始めて理由を示します。
- 反映後に本番とプレビューの設定の更新番号（revision）が一致しないアプリは、成功でも注意として示します。

「失敗・未実行だけ選び直す」は、成功以外のアプリを対象に段階 1 へ戻します。差分は取り直して確認します。

件数が多いとき（200 件超）は、実行結果の一覧を全件描画せず、件数の要約と、問題のあるアプリ・処理中のアプリを優先して表示します。全件は「結果JSONを保存」で確認できます。

## バックアップと戻し方

- 本番へ反映する前に、反映前の本番設定を JSON で保存します（変更のある JS/CSS はファイル本体も含みます）。「変更を中止」では、中止前のプレビューの設定を保存します。
- バックアップの形式はプレビュー反映の設定 JSON と同じです。プレビュー反映の反映元（設定JSON）にそのまま読み込めます。
- バックアップを保存できない場合は反映しません（「反映前の確認で止めました」）。本体を保存できなかった JS/CSS ファイルは、結果画面に一覧で示します。
- バックアップ JSON の本体は、保存したファイルとは別に、画面のメモリにも保持します（結果の「バックアップから戻す」で使うため。再読み込みで消えます）。結果 JSON・記録の Markdown には本体を含めません（JS/CSS の本文を含み得るため）。
- **本番へ反映した後の戻し方**：結果画面の「バックアップから戻す」を押します。「反映元アプリから本番へ」に切り替わり、反映元＝そのバックアップ、反映先＝そのアプリ、項目＝バックアップにある反映可能な項目、反映先だけの一覧・グラフ・アクションの保持＝OFF（反映で追加された設定を外すため）、参照先変換＝空、目標＝本番までに設定して段階 1 を表示します。「差分を抽出する」で戻す内容を差分で確認し、選んで直してから、通常どおり反映先のプレビューへ書き込み、本番へ反映します。**本番への反映は取り消せません。削除したフィールドの値は戻りません。**
- **変更を中止した後の戻し方**：同じく「バックアップから戻す」で、破棄した変更（中止前のプレビューのバックアップ）をプレビューへ戻せます。この場合の目標は、本番へは反映しない「プレビューまで」です。
- 保存したバックアップファイル（`kind: 'kintone-deploy-backup'`）は、「反映元アプリから本番へ」の段階 1 で「設定JSONから取得」を選んで読み込んでも、同じ「バックアップから戻す」の設定になります（反映先は、バックアップ内のアプリに合わせます。複数アプリのバックアップは、アプリを選ぶと反映先も合わせます）。
- 戻している間は「バックアップから戻しています」と表示します（段階 1〜4）。**フィールドの削除は行わないため、反映で追加したフィールドは残ります。削除したフィールドの値は戻りません。** 反映元・反映先・保持・参照先変換を変える、バックアップに無い項目を加えると、戻す状態を終えます（自動で設定した値のうち、変えていないものは戻す前の値に戻します）。
- 戻している間に画面を閉じて開き直した場合は、戻す前の入力で通常の状態として開きます。

## 反映元アプリから本番へ（開発・検証用アプリの設定を、選んで反映する）

パネル上部の「操作」で、「反映元アプリから本番へ」（既定）と「プレビューの変更を公開」（上の流れ）を切り替えます。実行中は切り替えられません。

「反映元アプリから本番へ」は、別のアプリ（開発・検証用）の設定を、本番アプリへ反映する流れです。差分を抽出し、反映する差分を**設定値 1 つずつ**選び（例：フィールドの「必須」だけ反映し、表示名は反映しない）、反映内容を直してから、反映先のプレビューへ書き込み、続けて本番へ反映します（アプリを更新）。プレビューへの書き込みは、プレビュー反映と同じ安全確認（実行直前の再取得と照合、revision 競合の通知）とバックアップを使います。

5 段階で進みます。段階 1〜3 では何も書き込みません。

1. **対象を選ぶ**
   - 反映元：「アプリの本番設定から取得」「アプリのプレビュー設定から取得」「設定JSONから取得」のいずれか。アプリIDには URL を貼り付けられ、入力中にアプリ名を確認します。「設定JSONから取得」で本番反映が保存したバックアップファイルを読み込むと、「バックアップから戻す」の設定になります（[バックアップと戻し方](#バックアップと戻し方)）。
   - 反映先：本番アプリ 1 件。書き込むのは反映先のプレビューで、そのあと本番へ反映します。
   - 反映する項目：プレビュー反映と同じ項目のチップ（既定はフィールド・レイアウト・一覧）。
   - 目標：「本番まで反映」（既定）か「プレビューまで（本番へは反映しない）」。
   - 「詳細設定…」で、反映先だけの一覧・グラフ・アクションを保持するか（既定は保持）と、参照先変換を指定します。
   - 進めない理由は「次に進むには：…」と固定フッターに出ます。「差分を抽出する」で段階 2 へ進みます。入力を変えると、抽出し直しが必要です（項目を減らすだけなら、抽出結果をそのまま使えます）。
  - 各段階の先頭に、キーボードで focus したときだけ見える「主な操作へ移動」があります。押すと、下部の固定フッターの主な操作（段階 1 は「差分を抽出する」、段階 2 は「内容の修正へ」など。押せないときはフッターの押せる操作）へ移ります。長い入力や変更の一覧を Tab で通らずに済みます（「プレビューの変更を公開」の段階 1〜3 にもあります）。
  - 幅 320px でも、上部の「操作」の選択肢は折り返して全部読めます。画面の見出し・表の列名・ボタンの説明は「ゲストスペースID」と書きます（入力欄の短い placeholder だけ「ゲストID」）。この表（`makeAppTable`）は他のツールと共通です。
2. **差分を選ぶ**
   - 抽出結果の要約（項目ごとの差分の有無・取得失敗）と、反映先プレビューの未公開の変更の有無を示します。「変更 N 件」は、下の項目の「選んだ変更 x/y」の y の合計（選べる変更の数）です。レイアウト・アクセス権・通知・JS/CSS の一覧などは全体で 1 件と数えるため、差分の計画の件数とは単位が違います。この違いは、見出しの「?」の吹き出しで説明します。
   - 反映先の反映状況（`GET /k/v1/preview/app/deploy.json`）も確認します。反映先を kintone が前回の反映の処理中（`PROCESSING`）のときは、「反映先は前回の反映を kintone が処理中です。完了してから抽出し直してください。」と警告で示し、先へ進めません（処理が終わってから「抽出し直す」を押します）。確認に失敗したときは「反映処理中かは未確認」と注意だけ示し、止めません。
   - 項目ごとのカードに、選んだ変更の数と、変更をまとまり（フィールド 1 つ・一覧 1 つなど）ごとに並べます。行は「場所・種類（追加・変更・削除）・前 → 後」です。グループ・項目単位でもまとめて選べます。フィールドや一覧を要素ごと追加・削除する行は、中の値を個別には選べません。
   - プラグインは、反映先に無いプラグインごとに 1 つずつ選べます（反映先のプラグインを外す変更は出ません。プラグイン固有の設定はコピーしません）。
   - ある変更を選ぶために別の変更が必要なとき（例：追加するフィールドを参照するルックアップ、選択肢の追加とその選択肢を初期値にする変更）は、一緒に選びます。外すときは、それを必要とする変更も外します。
   - 計算式（計算フィールドと、文字列（1行）の自動計算の `expression`）と、一覧の絞り込み条件・並び順、レコード権限の条件、レコード条件通知・リマインダー通知の条件、プロセス管理のアクションの条件、グラフ・アプリアクションの条件が、反映先に無く反映元にだけあるフィールドを参照するときも、そのフィールドの追加を項目をまたいで一緒に選びます。追加を選ばなければ「参照するフィールド「region」が反映先にありません。反映元にあるフィールドなので、フィールド設定で「region」の追加も選ぶか、この項目を除外してください。」（計算式は「計算式が、反映先に無いフィールド「shipping」を参照しています」）と示して進めません。式・クエリから参照とみなすのは、引用符の中の値・関数（`LOGINUSER()` など）・数値・演算子を除き、反映元か反映先のどちらかに実在するフィールドコードと一致した語だけです（実在しない語で既存の反映を止めません）。プレビュー反映も同じ規則で、レコード権限・レコード条件通知を選ぶとフィールド設定も取得します。
   - キーワードと種類（追加・変更・削除）で絞り込めます。絞り込み中の「表示中をすべて選ぶ／外す」は、表示中の変更だけが対象です。件数が多い項目は畳んであり、開いたときに描画します。
   - 取得失敗の項目を選んだままでは進めません。「この項目を反映しない」で外すか、抽出し直します。選ばなかったフィールドを参照する一覧など、選んだ内容の組み合わせの問題は、項目のカードと画面下に示します。
   - 反映元と反映先で、同じコードのルックアップ・関連レコード一覧（や同じ名前のアクション）の参照先アプリが違い、参照先変換に入れていないときは、「参照先変換の候補があります」と警告で示します（候補は `previewReflectStandalone` の `lookupCandidates`。プレビュー反映と同じ求め方で、根拠は反映先の現在の設定だけです）。入れずに反映すると、反映先の参照先が反映元（開発用アプリ）のアプリに書き換わり、本番まで反映されます。「候補を参照先変換に追加して差分を取り直す」で、詳細設定の参照先変換へ候補を加えて抽出し直します（入力済みの変換は上書きしません。反映先の参照先が複数に食い違うものは自動では入れず、食い違いを示します）。参照先変換は入力の署名に含まれるため抽出し直しになりますが、この操作での抽出し直しは、書き込み前に止まったあとの抽出し直しと同じ規則で、同じ変更の選択と同じ場所の入力欄の修正を引き継ぎ、引き継げなかった件数を示します（JSON での修正は引き継ぎません）。フィールド設定・アクション設定を反映する項目に含めているときだけ出します。バックアップから戻している間は、候補を示すだけで追加の操作は出しません。
   - 「選択と修正を保存」「選択と修正を読み込む」（段階 3 にもあります）で、選んだ変更と修正を JSON ファイルで受け渡せます（[選択と修正の保存・読み込み](#選択と修正の保存読み込み承認を待つ間や別の担当者への受け渡し)）。
3. **内容を修正**
   - 選んだ変更の主な値（表示名・必須など）を入力欄で直せます。既定の値と違う入力欄は強調され、「元に戻す」で戻せます。
   - 項目ごとに「JSONで編集」で、反映先へ送る設定の JSON を直接直せます（JS/CSS・プラグインを除く）。JSON で直している間は、その項目の選択・入力欄より JSON を優先します（「JSONでの修正を取り消す」で戻せます）。優先している間、入力欄には JSON の値を表示し、入力欄は使えません。JSON の修正を取り消すと、入力欄は取り消す前の入力欄の修正（なければ既定の値）に戻ります。
   - JSON の入力欄に「JSONを適用」していない変更（構文の誤りで適用できなかったものを含む）があるうちは、最終確認へ進めません（適用しないまま進むと、直した内容が送られないため）。「JSONの編集を閉じる」で、適用していない変更を捨てられます。
   - 修正のたびに、反映される内容の要約と、修正内容の問題を示します。直さない場合は、そのまま最終確認へ進めます。
   - 選択肢を持つフィールド（ドロップダウン・ラジオボタン・チェックボックス・複数選択）の初期値が、送る設定の選択肢に無いときは、入力欄・JSON の段階で「初期値「X」が選択肢にありません」と示して最終確認へ進めません（ラジオボタンは初期値が選択肢のどれかである必要があります）。同じ検査を実行時の書き込み前の計画の作り直しでも行い、書き込む前に止めます。
   - 状態欄は、段階を移るたびにその段階の文言に替わります（段階 3 は「内容を確認し、必要なら直してください。まだ書き込んでいません。」）。
4. **最終確認**
   - 経路（反映元 → 反映先のプレビュー → 本番）、項目ごとに選んだ変更・修正した値・変更の要約、削除される設定、反映先プレビューの未公開の変更、バックアップ（反映前のプレビューと、本番へ反映する前の本番）、取り消し方を示します。
   - 反映先プレビューに以前からの未公開の変更があるときは、「一緒に本番へ反映されます」として了承のチェックが必要です。未公開の変更があるか確認できなかったときも、「確認できませんでした。本番へ反映すると、プレビューの内容がすべて本番へ反映されます」として了承が必要です。了承しないと、本番まで反映は実行できません。
   - 参照先変換の候補を入れないまま進むときは、「参照先変換の候補」を未公開の変更の了承の前に同じ警告で示します（追加の入力は求めません）。実行すると、記録の Markdown（「注意: 参照先変換の候補」）と結果 JSON（`lookupCandidates`）に残ります。
   - 確認のチェックと、反映先アプリIDの入力が揃うと、実行ボタンが押せます。入力欄で Enter を押しても実行しません。段階 1〜3 のどこかを変えると、確認は解除されます。
5. **結果**
   - 反映先プレビューへの書き込みの進捗（項目ごと）と、本番への反映の状態（上の「結果の状態」と同じ表示）を示します。結果JSON・記録のMarkdownを保存・コピーできます。
   - 本番へ反映しなかった場合（書き込みの失敗・中止・確認の食い違い・未公開の変更の了承なし）は、理由とともに警告で示し、反映先プレビューの状況を言い分けます。書き込みが済んでいるときは「反映先プレビューには書き込み済みです」と、「プレビューの変更を公開」から続きを実行できることを示します。1 件も書き込めていない（すべて失敗・未実行）ときは「反映先プレビューは変わっていません。」、一部の項目や操作だけ書き込めたときは「反映先プレビューには一部だけ書き込まれています。差分を取得し直して現在の状態を確認してください。」と示します（「書き込み済み」「続けて本番へ反映できます」とは言いません）。結果 JSON・記録の Markdown も同じ言い分けです。
   - 本番まで反映が成功した（または完了を確認できない）結果と、プレビューまですべて書き込めた結果には、「反映後の内容を確認する」を出します（[反映後の内容の確認](#反映後の内容の確認)）。
   - 結果に「バックアップから戻す」を出します。本番へ反映した（成功・完了を確認できない）ときは反映前の本番のバックアップを、それ以外（本番へ反映しなかった・失敗した・目標が「プレビューまで」）は反映先プレビューへの書き込み前のバックアップ（目標はプレビューまで）を戻す内容にします。

### 書き込み前に止まったとき

差分の抽出の後に反映先が更新されたなどで、書き込み前の検査（再取得と照合）で止まったとき（まだ何も書き込んでいません）は、抽出結果を古いものとして扱います。段階 2〜4 の主ボタン（「内容の修正へ」「最終確認に進む」「実行」）は使えず、「差分を抽出し直す」へ案内します（段階 2・3 の案内とフッターに出ます）。選んだ差分や入力欄の修正を見直すことはできます。

抽出し直すと、前回の選択と入力欄の修正をできるだけ引き継ぎます。同じ変更 ID（`change.id`）の選択、同じ場所（`pointer`）の入力欄の修正が対象で、更新後の差分に無いものは引き継げません。引き継げなかった件数（選択・入力欄の修正・JSON での修正の項目数）は、ステータスと段階 2 に示します。JSON での修正は、前回の反映先を土台にした設定全体のため引き継ぎません。入力（反映元・反映先・保持・参照先変換）を変えたときは引き継ぎません。

### 選択と修正の保存・読み込み（承認を待つ間や別の担当者への受け渡し）

ブラウザの永続ストレージは使わないため、ページを読み込み直すと、選んだ変更や入力欄・JSON での修正は消えます。数百件の差分から選んで直した作業を、承認を待つ間や別の担当者へ渡すときは、段階 2・3 の「選択と修正を保存」で JSON ファイルに保存し、差分を抽出し直したあとに「選択と修正を読み込む」で戻します。どちらも書き込みません。

- 保存する内容：種類（`kind: kintone-source-deploy-selection`）と版、作成日時、反映元・反映先（アプリID・ゲストスペースID・アプリ名・反映元の取得方法）、反映する項目、保持・参照先変換・目標、項目ごとの選んだ変更の ID（と、差分にあって選ばなかった変更の ID）、入力欄の修正（pointer と値）、JSON での修正。JS/CSS の本文・バックアップ本体は含めません。ファイル名は `選択と修正_反映元-<名前>(app<ID>)_反映先-<名前>(app<ID>)_<日時>.json` です。
- 読み込み：現在の抽出結果へ、抽出し直したときの引き継ぎ（`carryOverSession`）と同じ規則で当てはめます。同じ変更 ID の選択、同じ場所（`pointer`）の入力欄の修正が対象で、保存後に差分へ増えた変更は既定どおり選びます。現在の差分に無い選択・修正は「当てはまらなかったもの」として件数を示します（段階 2・3 の案内と状態欄）。ファイルに含まれる項目は、現在の選択と修正をファイルの内容に置き換え、含まれない項目は変えません。
- JSON での修正は、反映先の設定を土台にした設定全体なので、保存時の反映先の設定（指紋）が現在と同じ項目だけ当てはめます。変わっていれば当てはめず、「JSON で直し直してください」と示します。
- 反映元・反映先（アプリID・ゲストスペースID・反映元の取得方法）が保存時と違うファイルは、違いを示して読み込みません（別のアプリへ誤って当てはめないため）。アプリ名は変えられるので比べません。保持・参照先変換が保存時と違うときは、読み込んだうえで注意を示します。
- 壊れたファイル・別種の JSON・新しすぎる版・20 MB を超えるファイル・JSON の変更を適用していない状態は、現在の選択と修正を変えずに、理由を示して拒否します。
- 読み込んでも最終確認は済みません。読み込みで確認は解除され、最終確認のチェックと反映先アプリIDの入力（反映先プレビューに未公開の変更があるときは了承も）が必要です。

### 反映後の内容の確認

結果の「反映後の内容を確認する」は、選んだ変更が、選んだ値（入力欄・JSON で直した値を含む）で反映先に入っているかを、読み取りだけで確かめます（書き込みません）。本番まで反映が成功した（または完了を確認できない）結果では本番の設定を、目標が「プレビューまで」ですべての項目を書き込めた結果では反映先のプレビューの設定を読み取ります。

- 実行したときに、選んだ変更の場所と、反映後にそこにあるはずの値（修正した値を含む。JSON で直した項目は、反映先の現在の値と違う場所）を控えます。反映後に読み取った設定（差分の抽出と同じ形）と比べ、「選んだ N 件はすべて反映されています」または「反映されていない変更 M 件」（場所・期待した値・現在の値）を示します。
- 比べるのは、選んだ変更の場所だけです。選ばなかった変更が反映先に残っているのは正常なので、問題に数えません。kintone が足した既定値など、期待した値に無い項目は許します。数値と文字列は、同じ表記なら同じ値とみなします。JS/CSS は、ファイル名で比べます（ファイルの中身は比べません）。
- 設定を取得できなかった項目は「確認できません」とし、確認できなかった変更が 1 件でもあれば「反映されています」とは言いません。完了を確認できなかった結果では、kintone の処理が続いていて、まだ反映されていないことがあります。
- 確認した日時と結果は、記録の Markdown（「反映後の内容の確認」）と結果 JSON（`verification`）に残ります。確認していないときは、記録に「確認していません」と残します。確認結果は直近の結果と一緒にメモリだけで持ち、ページを読み込み直すと消えます。
- 実装は `deploy/sourceVerify.ts`（期待する内容の組み立て・判定・文言。DOM 非依存）と `tabs/deploy-source-standalone.ts` の `verifySourceDeployStandalone`（`fetchBundle` で読み取り、差分の抽出と同じ `buildReflectSectionPlan` で PUT 形にする。`src/reflect/` は変えていません）です。

### エンジンとの取り決め

画面は、エンジンを `tabs/reflect-standalone.ts`（差分の抽出 `previewReflectStandalone`・選択の作り直し `composeReflectSelectionStandalone`・アプリ名の確認 `resolveReflectAppsStandalone`）、`reflect/selection.ts`（設定値 1 つずつの変更への分解）、`tabs/deploy-source-standalone.ts`（`runSourceToProductionStandalone`）と、`reflect/selectionTypes.ts`・`deploy/sourceTypes.ts` の型だけで使います。

- 選ぶたびに `composeReflectSelectionStandalone` で、送る設定と計画を作り直します。実行には、選んだ変更がある項目だけを `reflect.scopes` に渡し、項目ごとの送る設定を `composed` に渡します（`composed` に無い項目は既定の計画どおり書き込まれるため、書き込む項目は必ず渡します）。
- 差分の抽出は `previewReflectStandalone(opts, setStatus, { checkTargetDeployStatus: true })` で行い、反映先の反映状況（`targetDeployStatus`: `processing` / `idle` / `unknown`）も返します。`processing` のときは `collectSelectionBlockers` が `processing` の理由を返し、段階 2〜4 の主ボタンを止めます。この確認はプレビュー反映の抽出では行いません（画面は変えません）。
- 計算式・クエリが参照するフィールドの判定には、反映元・反映先のフィールドコード（システムフィールドを含む）を `knownFieldCodes` として渡します（`buildReflectSectionPlan`・`composeReflectSelectionStandalone`・`runApplyPreviewStandalone` が同じ規則を使います。`reflectRequiredFields(key, after, knownFieldCodes)`・`kintone-query.ts` の `extractQueryFieldCodes` / `extractExpressionFieldCodes`）。項目をまたぐ連動は `reflect/selectionRequires.ts` の `attachFieldAdditionRequires` が、セッションを作るとき（`createSourceSession`）に付けます。
- 差分の抽出時の `baseline`（`reviewBaseline`）と `targetPending` をそのまま渡します。未公開の変更の了承は `allowPendingChanges: true` で渡します。
- 抽出結果は入力の署名と結び付けます。署名は、反映元の種類・アプリ・設定JSON、反映先、保持、参照先変換です。項目は含めず、抽出時の項目の部分集合なら使い続けます。
- バックアップの JSON 本体は、`DeployRunResult.backup.content`（`runDeployStandalone` の結果。`runSourceToProductionStandalone` は `deploy.backup.content`）と、`apply.backup`（`runApplyPreviewStandalone` の反映前のプレビュー）から取ります。戻す内容の選び方と段階 1 へ設定する内容は `deploy/sourceRestore.ts`（DOM 非依存）に置きます。結果 JSON を作る `buildDeployResultJson` は `content` を含めません。

画面は `src/entries/deploy-source-ui.ts`（段階の移動・最終確認・実行・結果）、`deploy-source-select.ts`（段階 2）、`deploy-source-edit.ts`（段階 3）、選択・修正の状態は `src/deploy/sourceSession.ts`、選択と修正の保存ファイルは `src/deploy/sourceSelectionFile.ts`、反映後の内容の確認は `src/deploy/sourceVerify.ts`、表示用の純粋関数は `src/deploy/sourceDisplay.ts`、記録の Markdown と結果 JSON は `src/deploy/sourceReport.ts` です。

## 制約

- 対象アプリは最大 1000 件です。まとめて反映は最大 300 件・同じゲストスペースのアプリだけです。
- 本番への反映と「変更を中止」を行うには、対象アプリのアプリ管理権限が必要です。
- 反映の依頼は 1 件ずつ（または 1 回のまとめ）送り、自動では再試行しません。通信が途切れた場合は「完了を確認できない」として示し、アプリの設定画面で状態を確認します。
- 本番反映では書き込みガードの例外として、`/app/deploy.json` への POST（プレビュー側の prefix・完全一致）だけを許可します。レコード API やほかの本番設定への書き込みは行いません。
- ブラウザの永続ストレージは使いません。画面の状態はメモリだけに持ち、ページを読み込み直すと消えます。閉じて開き直したときは、同じページが表示されている間に限り、直前の操作（反映元アプリから本番へ／プレビューの変更を公開）とその結果、「反映元アプリから本番へ」の段階 1 の入力（反映元・反映先・項目・目標・詳細設定）、「プレビューの変更を公開」の対象と設定を表示します（`entries/deployMemory.ts`。ページの要素に載せて受け渡します）。差分の抽出結果は引き継がないため、「差分を抽出する」で抽出し直してください（古い差分で書き込まないため）。

`test:deploy-dom` は、エンジンを合成エンジンに差し替えて、画面の 4 段階・進めない理由・差分確認の表示・取得失敗を選んだままでは進めないこと・最終確認の入力と Enter・条件変更での確認解除・実行中の状態更新・成功／部分失敗／blocked／中止の表示・二重実行防止・Markdown と JSON の保存・1000 件の実行・320〜1440px の横はみ出しを実ブラウザで検証します。実アプリには通信せず、画面と結果は `.iter-shots/deploy-lite-dom/`（Git 管理外）に保存します。

同じコマンドの後半（`tools/test-harness/deploy-engine-scenarios.cjs`）では、エンジンを差し替えず、画面と実エンジンを束ねたまま、通信（`kintone.api`・`fetch`）だけを合成 kintone に差し替えて検証します。合成 kintone は、本番とプレビューの全比較項目の GET（revision はアプリ単位）、`POST /preview/app/deploy.json`（確認時のプレビュー revision と食い違えば `GAIA_CO02` で拒否。受け付けたら PROCESSING → SUCCESS／FAIL／CANCEL。revert ならプレビューを本番へ戻す）、状態確認の GET、ファイル本体の GET を再現し、それ以外の書き込みと想定外の URL は例外にして失敗させます。確認する内容は次のとおりです。各シナリオで、書き込みが deploy.json の POST だけであることも確認します。

- 1 アプリの本番反映：削除フィールドの警告、依頼は 1 回で確認時の revision を添えること、バックアップ（反映前の本番）の保存が依頼より前であること、成功後に本番とプレビューの revision が一致すること。
- 未公開の変更なし（revision 一致）のアプリは選べず、設定本体を取得しないこと。
- 確認後（最終確認から実行まで、または 1 アプリずつの実行の途中）にプレビューが更新されたとき、該当アプリは依頼せず「確認後に更新」にし、実行前なら何も依頼せずバックアップも保存しないこと。
- 1 アプリずつ反映で 2 件目が失敗したとき、3 件目を依頼しないこと。依頼が権限エラーで拒否されたとき「失敗」にすること。
- まとめて反映で 1 件失敗したとき、依頼は 1 回で全件を含み、ほかは「取り消し」になること。
- 変更を中止：`revert: true`、バックアップは中止前のプレビュー（`environment: 'preview'`）。
- JS/CSS：反映で外れるファイルの本体を取得できないときは依頼せず止め、取得できるときはバックアップの `file._content` に埋め込むこと。
- ゲストスペースのアプリは `/k/guest/{id}/v1/...`（設定・依頼・状態確認・ファイル本体）を使うこと。
- 実行中の「中止」：依頼の前なら依頼せず未実行、完了待ちの途中なら「完了を確認できない」にすること。

「反映元アプリから本番へ」の画面（5 段階）も同じコマンドで検証します。エンジン（差分の抽出・選択の作り直し・連続反映）を合成エンジンに差し替え、操作の切り替え、進めない理由、差分の選択（行・グループ・すべて・requires の連動・絞り込み・取得失敗で進めない・選択の組み合わせの問題の表示・3000 件でも固まらないこと）、修正（入力欄と元に戻す・JSON の適用・誤り・取り消し）、最終確認（未公開の変更の了承・確認できなかったときの了承・ID 入力・Enter で実行しない・条件変更での解除）、`runSourceToProductionStandalone` に渡る内容（composed・goal・allowPendingChanges・scopes・baseline）、結果（成功・プレビューまで・本番へ反映しなかった・書き込みの失敗・本番への反映の失敗・中止・書き込み前の停止・実行中の例外）、二重実行の防止、320〜1440px の横はみ出し無しを確認します（`tools/test-harness/deploy-source-scenarios.cjs`）。実エンジンとの結合は、エンジン側のテストと結合ハーネスで確認します。

さらに同じコマンドの最後（`tools/test-harness/deploy-source-engine-scenarios.cjs`）で、この 5 段階の画面を実エンジンのまま合成 kintone につないで検証します。合成 kintone は、反映元（#101）と反映先（#202）の本番・プレビューの全項目の GET、`GET /app.json`、反映先プレビューへの設定の書き込み（`PUT` / `POST`。revision を照合して `GAIA_CO02`、成功で revision を進めて内容を反映）、`/preview/app/deploy.json` の POST と状態確認の GET（PROCESSING → SUCCESS / FAIL。SUCCESS で本番 = プレビュー）、ファイルの取得・アップロードを再現します。本番・反映元への設定の書き込みと想定外の URL は例外にして記録し、各シナリオの最後に違反が無いことを確認します。確認する内容は、画面の表示と、合成 kintone が受け取った送信内容の両方です。

- 必須だけを選ぶと、フィールドの `PUT` の body は必須だけが反映元の値で、表示名・重複禁止は反映先のままであること。追加フィールドを選ばなければ `POST` は無く、続けて deploy.json に 1 回だけ依頼して本番が更新されること。バックアップは 2 つ（反映前のプレビュー、本番へ反映する前の本番）で、それぞれ最初の書き込み・依頼より前であること。
- 入力欄で直した値（と、「元に戻す」で既定へ戻した値）が送信内容になること。「既定: はい / いいえ」の表示。
- 一覧の JSON 編集が、送信内容に JSON のとおり出ること。JSON の誤り（構文・フィールドの種類の変更・フィールドの削除）と、適用していない JSON の変更があるうちは、最終確認へ進めないこと。
- 選ばなかった追加フィールドを参照する一覧・レイアウトを選ぶと、進めない理由を示し、何も書き込まないこと。
- 項目の一部だけに変更を選んだとき（例：一覧の変更をすべて外す、一覧だけを選ぶ）、書き込みは選んだ項目だけで、抽出時の `baseline` の照合で止まらないこと。
- 目標「プレビューまで」では deploy.json を依頼せず、本番は変わらないこと。
- 反映先に以前からの未公開の変更があるとき、最終確認で了承が必須で、了承して実行すると一緒に本番へ反映されること。
- 差分の抽出の後に反映先プレビューが更新されたときは、書き込み前に止まり（書き込み・依頼・バックアップなし）、抽出し直して実行できること。
- 書き込みの途中で失敗したとき（レイアウトの PUT が拒否）は本番へ反映せず、依頼しないこと。1 件も書き込めなかったときの注記は「反映先プレビューは変わっていません。」、一部だけ書き込めたときは「一部だけ書き込まれています」で、「書き込み済み」とは言わないこと。本番への反映が FAIL のときの表示。
- 選択肢にない初期値は入力欄の段階で止め、計算式・一覧の絞り込み条件・レコード権限の条件が参照する追加フィールド（反映先に無い）は、選ぶと追加も連動して選ぶこと。反映先が反映処理中のときは、抽出の時点で示して先へ進めず、処理が終わってから抽出し直すと進めること。閉じて開き直したとき、入力と直前の結果を表示すること。段階の先頭の「主な操作へ移動」で主な操作へ移れること。
- 中止：書き込み中は次の書き込みの前で止まり、本番へは反映しないこと。本番反映の完了待ち中は「完了を確認できない」になること。
- 書き込み前に止まったときの扱い：抽出結果を古いものとして扱い、段階 2〜4 の主ボタンが使えず「差分を抽出し直す」へ案内すること。抽出し直すと、選択（同じ変更 ID）と入力欄の修正（同じ pointer）を引き継ぎ、更新で消えた差分は引き継げなかった件数として示すこと。
- JSON で直した項目の入力欄に JSON の値が出て（入力欄は無効）、JSON の修正を取り消すと入力欄の修正（なければ既定）に戻ること。
- プラグインを 1 つずつ選べ、選んだ ID だけを追加し、反映先のプラグインが外れないこと。
- バックアップから戻す：反映 → 戻す → 本番が反映前と同じ内容になること（追加したフィールドと、その配置だけが残る。反映で追加した一覧は外れる）。結果画面のボタン、設定JSONから読み込んだバックアップファイル（複数アプリのバックアップでアプリを選ぶと反映先も合う・変えると戻す状態を終える）、「プレビューまで」の結果から戻す場合（目標はプレビューまで）。結果 JSON にバックアップ本体を含めないこと。「プレビューの変更を公開」の結果（1 アプリ・複数アプリ・中止）から「反映元アプリから本番へ」に切り替わること。

画面は `src/entries/deploy-lite-ui.ts`（操作の切り替えと「プレビューの変更を公開」）、表示用の純粋関数は `src/deploy/display.ts`、計画・記録・結果 JSON の組み立ては `src/deploy/report.ts`、エンジンとの取り決めは `src/deploy/types.ts` です。
